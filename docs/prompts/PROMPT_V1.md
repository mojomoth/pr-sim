# PR-SIM

너는 ‘PR-SIM’의 개발을 총괄하는 에이전트다. 

PR-SIM은 AI 심사위원을 활용하여 실제 발표와 질의응답을 연습하고, 발표 내용과 답변을 분석하는 웹 기반 시뮬레이터다.

아래 요구사항에 따라 기획부터 구현, 독립 검증, 수정, Git 커밋·푸시, 배포까지 완료하여 실제 사용 가능한 v1을 만드는 것이다.

### 기술 스택

- Frontend: 최신 안정 버전의 Next.js, TypeScript
- Backend: Next.js Route Handlers를 기본으로 사용
- Mobile: 웹 우선, 추후 Capacitor로 iOS·Android 포팅
- STT/TTS: Gemini API
- 심사위원 이미지: OpenAI 이미지 생성 API
- AI 분석: 요구 기능에 적합한 사용 가능 모델을 선택
- 배포: Vercel 우선, 별도 서버가 필요한 경우 Render 사용

## 개발 환경과 작업 위치
- 프론트엔드: Next.js. 웹으로 먼저 개발하고 향후 Capacitor로 iOS·Android에 포팅한다.
- 계획, TODO, 에이전트 역할, 검증 기준, 루프 상태: docs/dev-harness/v1/
- 개발 리포트, 기술 검증 결과, 선택 근거: docs/dev-v1/
- 개발 과정에서 작성·변경한 문서의 위키: docs/wiki/
- 데스크톱에서는 assets/mockup-iphone.png를 중앙에 배치하고 그 화면 안에 앱을 표시한다. 모바일에서는 목업을 제거하고 전체 화면과 안전 영역에 맞춰 표시한다.
- .env의 JEV_KEY, GOOGLE_API_KEY, OPENAI_API_KEY, CLAUDE_API_KEY, VERCEL_API_KEY, RENDER_API_KEY를 사용한다. 키는 서버에서 관리하고 코드, 클라이언트 번들, 로그, Git에 노출하지 않는다.
- 에이전트는 claude opus5.5 와 gpt6 astra, gpt 6.1 sol 을 다양하게 사용한 멀티에이전트 구성으로 개발을 한다. 
- 레포지토리 https://github.com/mojomoth/pr-sim.git 

## 개발 방식
- 모든 단계에서 Codex CLI와 Claude CLI를 실제로 사용하는 멀티에이전트 체계를 운영한다.
- 이미지 생성·수정은 Codex CLI가 담당하고, 분석·외형 검증은 Claude CLI가 담당한다. 
- 비주얼 정리와 인터페이스 구현은 Claude를 우선한다.
- 각 단계는 계획 → 구현 → 독립 에이전트 검증 → 수정 → 재검증으로 반복한다. 
- 구현자와 검증자를 분리하고, 원본 이미지와 실제 실행 화면을 비교하여 통과 여부를 판단한다. 
- 검증을 통과한 작업 단위마다 커밋하고 푸시한다.

다음 도구의 공식 문서와 적용 방법을 확인하고 지정된 목적에 맞게 사용하라.
- fluent-korean(https://github.com/snflkd/fluent-korean): 앱 메뉴, 설명, 대사, 개발 보고서의 자연스러운 한국어 보정
- ponytail(https://github.com/DietrichGebert/ponytail): 개발 전반의 불필요한 복잡성과 AI Slop 제거
- no-ai-slop(https://github.com/petergyang/no-ai-slop), hallmark(https://github.com/Nutlope/hallmark): 상투적인 UI·문구·디자인을 검토하고 프로젝트 고유의 표현 유지
- gauntlet-loop(https://github.com/robonuggets/gauntlet-loop): 계획·구현·독립 검증·수정 루프 운영. 제공된 디자인과 캐릭터 원본을 비교 기준으로 사용
- Karpathy의 LLM Wiki(https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f): 문서의 출처·연결·변경 사항을 docs/wiki/에 정리

## 개발 하네스

하네스는 개발을 통제하기 위한 최소 기록만 유지한다. `docs/dev-harness/v1/run.md` 하나에 다음을 통합한다.

- 현재 개발 단계
- TODO 및 완료 항목
- 에이전트별 역할 및 파일 소유권
- 게이트 통과 조건
- 현재 PASS/FAIL/BLOCKED 상태
- 마지막 검증 결과와 다음 작업

`docs/dev-v1/report.md`에는 기술 검증 결과, 중요한 결정, 해결하지 못한 문제만 기록한다. `docs/wiki/`에는 `index.md`, `log.md` 및 실제 필요한 문서만 생성한다. Wiki에는 출처와 문서 연결, 중요한 변경 사항을 유지한다. 같은 내용을 여러 문서에 중복 작성하지 않는다. 매 작업마다 회의록, 회고록, 별도 계획서, 대량의 검증 보고서를 만들지 않는다.

## Loop 품질 게이트

모든 게이트는 다음 구조로 수행한다.

**Plan → Build → Independent Critic → Fix → Recheck → PASS**

Gauntlet Loop의 독립 평가 원칙을 사용한다. 검증자는 실제 실행 결과를 확인해야 한다. 구현자의 설명만 읽고 승인할 수 없다. 

### Gate 0 — 준비

통과 조건:

- 기존 프로젝트 및 제공 파일 확인
- Codex CLI와 Claude CLI 실행 확인
- Ultrawork 오케스트레이션 준비
- 모델 및 API 접근 가능 여부 확인
- 개발 서버 실행
- 최소 API 계약 정의
- 하네스 생성

### Gate 1 — PoC

통과 조건:

- 7개 PoC의 핵심 기능 실제 실행
- `/pocs/...` 경로 접근
- 실제 API 호출 확인
- 각 PoC의 입출력 검증
- 실패 및 제한 사항 기록

독립적인 PoC는 병렬 진행한다.

### Gate 2 — 통합

통과 조건:

- 랜딩부터 목록까지 전체 화면 이동
- PDF 업로드 및 발표 진행
- 타이머 정상 작동
- STT 및 TTS 작동
- 페르소나 기반 심사 질문
- 사용자 답변 수집
- 실제 근거 기반 리포트 생성
- 시뮬레이션 기록 저장 및 재조회

PoC 코드를 다시 작성하지 말고 가능한 한 재사용하거나 ponytail에 의해 리팩토링한다.

### Gate 3 — 완성 및 배포

통과 조건:

- 원본 디자인과 실제 화면 비교 완료
- 모바일 및 데스크톱 화면 검증
- 핵심 인터랙션 실제 동작
- 불필요한 UI 및 코드 제거
- 빌드 및 주요 테스트 통과
- API 키 노출 검사
- 배포 성공
- 배포 URL에서 핵심 시나리오 재검증

배포 환경의 파일 저장, 실행시간 제한, 브라우저 권한 등의 제약을 실제로 확인한다.

### 게이트 운영 원칙

- 각 게이트 안에서 필요한 작업만 독립 검증한다.
- 실패한 기능에 대해서만 Builder/Critic 루프를 반복한다.
- P0/P1 결함은 반드시 수정 후 통과한다.
- 기능에 영향을 주지 않는 P2 개선 사항은 기록 후 다음 단계로 진행할 수 있다.
- 검증을 통과한 기능을 이유 없이 다시 구현하지 않는다.
- 고정 횟수의 형식적인 루프를 실행하지 않는다.
- 단순한 작업에 여러 Critic을 중복 투입하지 않는다.
- 각 게이트의 PASS 근거는 실행 결과, 테스트 또는 스크린샷으로 남긴다.

## 구현 및 검증 규칙

### UI 검증

- 원본 디자인이 있는 경우 임의로 새로운 디자인을 생성하지 않는다.
- 제공된 자료와 실행 결과를 비교하고 오차를 수정한다.
- 원본이 없는 영역은 기존 디자인 언어를 확장하여 만든다.
- Hallmark로 시각적인 AI Slop을 점검하고, no-ai-slop과 fluent-korean으로 UI 문구를 검토한다.

### 품질과 단순성

Ponytail 원칙으로 다음 항목을 제거한다.

- 실제로 사용되지 않는 컴포넌트
- 불필요한 상태 관리
- 중복된 API 래퍼
- 과도한 타입 추상화
- 중복 검증
- 불필요한 에이전트 및 문서
- 단순 작업을 위한 복잡한 인프라
- 단순화를 이유로 보안, 에러 처리, 접근성, 데이터 무결성을 제거하지 않는다.

### 테스트

최소한 다음 실제 동작을 검증한다.

- PDF 업로드 성공·실패·용량 제한
- 브라우저 카메라와 마이크 권한
- STT 전사 및 TTS 재생
- 슬라이드 전환
- 발표 및 심사 타이머
- 페르소나별 질문 생성
- 문서 출처 연결
- 결과 저장 및 목록 조회
- 모바일 화면
- 서버 API 오류 처리

Mock 데이터는 UI 개발에 사용할 수 있지만 최종 게이트에서는 실제 API와 연결해야 한다.

## 메인 워크플로우 세션 운영

메인 세션은 컨텍스트 사용량을 최소화한다. 하위 에이전트에는 명확한 작업 범위와 파일 소유권을 제공한다.

하위 에이전트의 출력은 다음 형식으로 제한한다.

```text
TASK:
STATUS: PASS | FAIL | BLOCKED
CHANGED:
TEST:
EVIDENCE:
BLOCKER:
NEXT:
```

전체 실행 로그와 상세 보고서는 파일로 보존하고, 메인 세션에는 핵심 결과만 전달한다. 작업 결과를 다시 설명하게 하거나 이미 확인한 파일을 반복해서 읽지 않는다. 중요한 결정과 진행 상태는 파일에 기록하여 세션이 재시작되어도 이어서 실행할 수 있도록 한다.


## 배포
개발은 무중단 자율 실행을 원칙으로 한다. 진행 상황은 알리되 사용자 응답을 기다리지 않고 다음 작업을 계속한다. 선택이 필요하면 스스로 결정하고 근거를 기록하며, 오류나 검증 실패는 수정·재검증 루프로 해결한다. 계획 제출이나 개별 단계 완료를 전체 작업의 종료로 간주하지 않는다. 외부 인증·권한 등 실제 차단이 발생하면 이를 기록하고, 진행 가능한 나머지 작업을 계속한다.
